Imagem e inicialização

1. Qual a diferença entre imagem e container?

A imagem reúne o código, o Node e as dependências. O container é uma execução dessa imagem. Posso iniciar quatro containers a partir da mesma imagem e cada um terá seu próprio processo.

Como o Dockerfile monta a API

O primeiro FROM abre a etapa de dependências com Node Alpine. WORKDIR define /app como diretório de trabalho. COPY leva a lista de dependências e o arquivo de versões para lá e RUN instala as bibliotecas de produção. O segundo FROM inicia a imagem final. COPY --from traz as bibliotecas e o outro COPY traz server.js. ARG recebe a versão durante o build. ENV deixa a versão disponível quando a API roda. USER node inicia o processo com um usuário sem privilégios de root. EXPOSE documenta a porta 3000 e CMD inicia o servidor.

2. Como a API espera o banco ficar pronto?

No Compose, a API depende dos healthchecks do MySQL e do Redis. No Kubernetes os pods podem começar em qualquer ordem. A API tenta criar a tabela e repete a tentativa a cada dois segundos se o MySQL estiver iniciando. A readinessProbe consulta /health, que testa o banco e o Redis. O Service encaminha tráfego aos pods prontos. A livenessProbe usa /live para verificar se o processo responde mesmo durante uma falha no banco.

Recursos e comunicação

3. Por que esses requests e limits?

O request é a quantidade que o agendador considera ao escolher um nó. O limit estabelece o teto do container. Na API comecei com 50m de CPU e 64Mi de memória, com limites de 250m e 128Mi. 50m equivale a 5% de um núcleo. São valores iniciais para uma API pequena em um notebook. Na etapa de operação, o request de CPU passa para 25m e o limite para 200m para facilitar o teste do HPA. Para ajustar esses números em produção, é preciso medir o consumo sob carga.

4. Qual é o papel de Deployment, ReplicaSet e Service?

O Deployment descreve a versão da aplicação e quantas cópias devem estar disponíveis. Ele gerencia ReplicaSets. Cada ReplicaSet cria ou repõe pods para chegar à quantidade desejada. O Service da API oferece um endereço estável. Seu seletor app=api coincide com o rótulo dos pods da API. Assim, o endereço continua funcionando quando uma atualização substitui os pods.

5. Por que base64 não protege senhas?

Base64 é uma codificação reversível. Quem consegue ler o conteúdo pode recuperar o texto original. Neste projeto, o Secret usa stringData com valores fictícios de laboratório. Em produção, usaria um gerenciador de segredos, controle de acesso por função, criptografia em repouso e rotação de credenciais. O arquivo .env local fica fora do Git.

Escala, recuperação e limites

6. Como funciona o HPA deste projeto?

O mínimo é 2 e o máximo é 6 réplicas. O alvo de 50% se refere à utilização média em relação ao request de CPU dos pods da API. Com request de 25m por pod, 50% corresponde a 12,5m por pod, em média. Os geradores consultam a rota inicial. Ao encerrar a carga, o HPA pode levar vários minutos para reduzir as réplicas. Resultado observado: registrar contagem inicial, pico e contagem final a partir de hpa-linhas.txt.

7. Quando usar rollout undo?

O rollback permite voltar a uma revisão anterior quando a nova imagem falha. O teste substitui a imagem 2.0 pela tag ausente-n3. No describe do pod novo, a seção Events permite identificar o motivo da falha ao obter a imagem. Com maxUnavailable igual a zero, o Deployment mantém as réplicas anteriores disponíveis enquanto a nova não fica pronta. Após o undo, a rota inicial deve voltar a confirmar a versão 2.0. Resultado observado: inserir o evento real, a revisão e a versão retornada.

8. Quais são as limitações?

O MySQL usa um Deployment com uma réplica e estratégia Recreate para que dois processos não disputem o diretório de dados. O PVC permite substituir o pod, mas uma cópia única do banco ainda gera indisponibilidade e o volume não substitui um backup. O Redis mantém apenas um contador que pode zerar em um reinício. Para produção, eu testaria a restauração de backups, adotaria replicação adequada para o banco e mediria latência e consumo antes de aumentar os limites da API.

Situação da coleta

A execução no Docker Desktop e a medição de réplicas ainda precisam ser registradas. As saídas abaixo podem ser incorporadas na versão editável do relatório depois dos testes.

Docker e persistência

Registrar a versão e /live no container isolado. No Compose, mostrar /health e o mesmo ID antes e depois de down e up. No Kubernetes, mostrar os nomes do pod antigo e do novo, o PVC e o mesmo ID após a troca.

Operação do cluster

Incluir kubectl get all, describe deployment api e rollout history. Registrar a escala 2, 4 e 2, a versão 2.0, o evento de falha no describe pod, a recuperação e os recursos depois de set resources.

Métricas e nó

Incluir get hpa -w antes, durante e depois da carga, top pods e describe node. Capacity indica o total do nó. Allocatable é a quantidade disponível para os pods depois das reservas. Allocated resources mostra a soma dos requests e limits dos pods alocados. Anotar valores de CPU e memória do nó usado e manter o namespace visível no registro.
